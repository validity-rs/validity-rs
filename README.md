# validity-rs

A Rust driver and fprintd-compatible D-Bus service for the **Synaptics/Validity
"match-on-chip" fingerprint sensors** found in many 2016–2018 ThinkPads, which
`libfprint` lists as *unsupported*.

> **Status: pre-alpha.** The full protocol works on real hardware (`06cb:009a`, ThinkPad
> T480): pairing, firmware upload, calibration, enrolment and identification, all in
> Rust. The D-Bus service passes its end-to-end tests with fprintd's own clients and
> `pam_fprintd`, but has not yet run on hardware. A Debian package is built and tested
> in CI ([packaging](docs/packaging.md)); it has not yet been installed on hardware.
> Do not rely on it for logging in.

## Why

Sensors such as `06cb:009a` (ThinkPad T480, T480s, X280, X1 Carbon 6th gen) do the
matching inside the chip and talk to the host over a proprietary, TLS-like
encrypted channel. `libfprint` does not support them. Until now the only working driver
has been [python-validity](https://github.com/uunicorn/python-validity) (MIT), together
with [open-fprintd](https://github.com/uunicorn/open-fprintd) (GPL-2.0). Both are hard
to install and barely maintained.

`validity-rs` is a **drop-in replacement for `fprintd`** on these devices. It exposes
the same D-Bus API (`net.reactivated.Fprint`), so `libpam-fprintd`, GNOME, KDE, LightDM,
screen lockers and the `fprintd-*` tools keep working unchanged.

## Supported devices

| USB ID | Sensor | Status |
|---|---|---|
| `06cb:009a` | Synaptics "Metallica MIS" | Protocol complete on hardware; service in testing |
| `138a:0090`, `138a:0097`, `06cb:009d` | Validity / Synaptics | Later (handled by python-validity) |

## Design principles

1. **Never lock anyone out.** The service fails safe. If the sensor, the
   firmware or the daemon misbehaves, authentication falls back to the password at once.
   Configure PAM so that the fingerprint is `sufficient`, never `required`.
2. **No biometric data leaves the chip.** Templates are stored and matched on the
   sensor. The host only manages the encrypted session and the flash records.
3. **Byte-exact against the reference.** The protocol is ported from python-validity
   and checked against it. Test vectors are generated by the reference on synthetic
   inputs, and recorded hardware sessions are replayed byte for byte.
4. **No proprietary blobs in this repository.** The Synaptics firmware extension and
   the command blobs come from Lenovo's driver package. They are verified by SHA-256 at
   install time; only offsets and hashes live here.
5. **No device secrets in this repository.** See *Privacy* below.
6. **Better than the reference by design.** Every open issue of python-validity and
   open-fprintd was triaged. Each one maps to a design requirement and a test:
   - recovery after suspend;
   - the device always visible with an explicit state;
   - no destructive action taken automatically;
   - verification only accepts the claimed user's own fingers: any of them for
     `VerifyStart("any")` (announced as `any`, as fprintd does for a device that
     identifies), only that one for a named finger. `fprintd-verify` without `-f`
     names the first listed finger itself, so use `-f any` to accept every finger
     (`pam_fprintd` always asks for `any`). Enrolling a finger already enrolled,
     by anyone, ends with `enroll-duplicate` (done), as in fprintd.

## Layout

```
crates/validity-proto    the protocol: USB transport (nusb, optional `usb` feature),
                         TLS-like channel (RustCrypto: ECDH P-256, AES-256-CBC,
                         HMAC-SHA256), pairing, firmware upload, calibration, flash,
                         on-chip database, enrolment, identification
crates/validity-daemon   net.reactivated.Fprint D-Bus service (zbus), polkit, logind
                         suspend handling, recovery
crates/validity-vendor   installs the Synaptics vendor files from Lenovo's package
                         (download, SHA-256 checks, Inno Setup extraction, atomic
                         switch into /var/lib/validity/vendor)
packaging/common         systemd unit, D-Bus activation file and bus policy, udev rule,
                         man page, AppStream metadata, example configuration
packaging/debian         Debian maintainer scripts (cargo-deb metadata: the daemon's
                         Cargo.toml)
ci/packages/             package builds and install/smoke/remove cycles (run.sh)
fuzz/                    cargo-fuzz targets for every parser and the handshake
tools/oracle/            python-validity scripts that generate the test vectors
ci/                      the CI, runnable locally (ci/run.sh) and end-to-end tests
```

A desktop app to enrol and manage fingerprints on desktops without one (XFCE, MATE,
LXQt) lives in its own repository, `fingerprint-settings`. It only uses the standard
fprintd API.

## Installing

On Debian 13 (trixie), from the `.deb` built by CI or by `ci/packages/run.sh debian`
(in `target/packages/debian/`):

```bash
sudo apt install ./validity-daemon_0.1.0-1_amd64.deb
```

The package depends on `fprintd` and takes over only its D-Bus activation file, so
fprintd's tools, `pam_fprintd` and desktops reach validity-daemon. Removing the
package gives fprintd its file back. During installation `validity-vendor install`
downloads Lenovo's driver package and installs the two Synaptics files the sensor
needs, checked by SHA-256. If the machine is offline, the installation still
succeeds, and you finish later with `sudo validity-vendor install`.

The package never changes PAM. To log in with a finger, install `libpam-fprintd`
and keep the fingerprint `sufficient`, never `required`, so that the password
always works. Enrol with `fprintd-enroll`.

Details, other distributions and the CI cycle: [docs/packaging.md](docs/packaging.md).

## Building and testing

Requirements: Rust 1.99 or later (edition 2024). For the daemon's integration tests you
also need `dbus-daemon`, and `curl` for validity-vendor's (it downloads with curl). No C libraries are needed: the USB transport is pure Rust.

```bash
cargo build
cargo test                                   # all tests
cargo test -p validity-proto <name>          # one test
ci/run.sh                                    # quick CI set
ci/run.sh all                                # everything (needs docker)
ci/run.sh distro:fedora                      # one job
ci/run.sh mutants-diff                       # mutation testing of the last commit
```

`ci/run.sh` is the CI: GitHub Actions calls the same jobs, inside pinned Debian 13
(trixie) containers. Debian is the reference target. Fedora, Arch Linux and Alpine are
tested too. The checks are:

- **Warnings:** none tolerated. They are denied in `Cargo.toml` itself, and
  `unsafe` is forbidden.
- **Lint and docs:** rustfmt, clippy and rustdoc.
- **Minimum Rust version:** 1.99.
- **Unit and integration tests**, including:
  - test vectors from the Python reference;
  - a full handshake against an independent fake sensor;
  - exact-boundary tests derived from mutation testing (cargo-mutants);
  - the replay machinery (log parser, `ReplaySensor`, masks, handshake checks) on
    synthetic logs in python-validity's debug-log format, whose sensor keys are
    signed by a test firmware key; real recordings are replayed only when
    `VALIDITY_TRACES` points to them, and never leave the machine.
- **End to end:** in a Debian container, the daemon runs with a fake sensor and is
  driven by fprintd's own `fprintd-enroll/verify/list/delete`, `pam_fprintd` (through
  `pamtester`) and a real polkit.
- **Fuzzing** of every parser and of the handshake: 30 s per target on each push,
  10 minutes weekly.
- **Mutation testing** (cargo-mutants) of both crates: every mutant must make a test
  fail. The code a push changes is checked on that push (`ci/run.sh mutants-diff`),
  all of it weekly (`ci/run.sh mutants`). The exceptions are argued one by one in
  `.cargo/mutants.toml`: equivalent mutants, and the few functions that only run
  against a real USB device.
- **Supply chain and repository hygiene:**
  - cargo-deny for licences, advisories, duplicates and sources;
  - a daily RustSec audit;
  - gitleaks over the whole history;
  - zizmor, which audits the workflows themselves;
  - a check against AI tooling attribution;
  - every action and image pinned by hash.

Enable the pre-push hook once per clone. It runs the quick set on a clean checkout of
each pushed commit:

```bash
git config core.hooksPath .githooks
```

### Hardware tests

These need the sensor and root access:

```bash
cargo build --release --example probe --example session
sudo target/release/examples/probe <synaWudfBioUsb.dll>
sudo target/release/examples/session <synaWudfBioUsb.dll> <calibration-file> list
sudo target/release/examples/session <dll> <calibration-file> identify 5
sudo target/release/examples/session <dll> <calibration-file> enroll <uid> <finger>
sudo VALIDITY_FWEXT=<file.xpfwext> target/release/examples/session <dll> <cal> reset   # erases the sensor
```

`VALIDITY_LOG=info|debug|trace` logs to stderr, each line prefixed with the seconds
since the start. To diagnose a problem, write the trace straight to a file:

```bash
sudo VALIDITY_LOG=trace target/release/examples/session <dll> <cal> enroll <uid> <finger> 2> session.log
```

The trace never contains command or reply contents (keys, templates, flash data), so
it can be shared. Its lines:

| Line | Meaning |
|---|---|
| `>plain> 3e (1 bytes)` | a command in the clear: opcode, length |
| `<plain< 3e (64 bytes, status 0000)` | its reply: opcode, length, status word |
| `>app> 5e (13 bytes)`, `<app< 5e (2 bytes, status 0000)` | the same over the encrypted channel |
| `>usb> 69 bytes`, `<usb< 85 bytes` | the USB transfers that carry them |
| `channel: handshake`, `channel: open` | the encrypted channel being opened |
| `wait: a finger (deadline 30s)` | a wait starts, with its deadline |
| `<int< 0300060000` | an interrupt; its first byte is the type (0 scan armed, 2 finger detected, 3 capture progress) |
| `<82< N bytes` | image data (calibration) |
| `WARN timed out after 2s waiting for the capture to start (last command 02, last interrupt none)` | a wait passed its deadline |

The daemon logs the same lines with `--trace-sensor-traffic`.

Recorded sessions can be replayed against the code with
`VALIDITY_TRACES=<dir> VALIDITY_DLL=<dll> cargo test --test replay`. Recordings contain
device secrets: they are never committed.

To study the protocol, read python-validity's `validitysensor/` next to
`crates/validity-proto/src`. The module names match.

## Waits and timeouts

No wait on the sensor is unbounded. Each one has a deadline
(`validity_proto::session::Deadlines`). When it passes, the operation fails with
`Error::Timeout`, and a warning names the last command and the last interrupt seen.

| Wait | Deadline | Longest seen in phase 0 |
|---|---|---|
| the finger, once the scan is armed (LED on) | 30 s, configurable | user dependent |
| scan armed after the capture command | 2 s | 6 ms |
| capture complete after the finger is down | 5 s | 856 ms |
| match result | 10 s | 829 ms (2 fingers enrolled) |
| each enrolment step | 5 s | 431 ms |
| image data (calibration) | 5 s | 103 ms |
| any other interrupt | 5 s | 6 ms |

Only the finger wait depends on the user. Its default is the same as pam_fprintd's
default timeout (30 s). In the daemon, set it with `finger_timeout_ms` in
`/etc/validity/validity.toml`. When it passes:

- a verification ends with `verify-no-match`, which is fprintd's result for a
  verification that ended without a matching finger;
- an enrolment reports `enroll-retry-scan` and arms the scan again, because fprintd
  keeps an enrolment running until the client stops it.

Any other deadline passing means that the sensor stopped answering. The run fails
with `verify-disconnected` or `enroll-disconnected`, which pam_fprintd treats as
"fall back to the password". The daemon then reboots the sensor and reopens it. If
the sensor does not even accept the reboot command, the daemon resets its USB port.

## Privacy

Captured USB sessions contain the **sensor serial number, pairing keys and TLS
session keys** of the capturing device. **Never commit raw captures.** Tests use
synthetic data. Replays of real recordings read them from outside the repository.
Do not commit flash dumps. `gitleaks` scans the whole history in CI.
