# Development guide

How validity-rs is built, tested and released. For the packages, the APT
repository and the release workflow in full, see [packaging.md](packaging.md).

## Design rules

1. **Never lock anyone out.** Every failure of the sensor, the vendor files,
   the daemon or the PAM module falls back to the password. Packages never
   change PAM, and the fingerprint is `sufficient`, never `required`.
2. **No biometric data leaves the chip.** Templates are stored and matched on
   the sensor; the host manages the encrypted session and the flash records.
3. **Byte-exact against the reference.** The protocol is ported from
   [python-validity](https://github.com/uunicorn/python-validity) (MIT). Test
   vectors are generated by the reference on synthetic inputs, and recorded
   hardware sessions replay byte for byte.
4. **No proprietary files and no device secrets in the repository.** The
   vendor files are downloaded and checked by SHA-256 at install time; only
   offsets and hashes live here. See [Privacy](#privacy).
5. **Nothing destructive by default.** The daemon never pairs, erases or
   flashes the sensor.
6. **fprintd's behaviour, exactly.** The daemon implements fprintd 1.94.5's
   `Manager` and `Device` objects, so every client works unchanged. Every
   open issue of python-validity and open-fprintd was triaged into a
   requirement and a test: recovery after suspend, the device always visible
   with an explicit state, no automatic destructive action, verification
   limited to the claimed user's fingers. open-fprintd (GPL-2.0) is read for
   behaviour only, never copied.

## Architecture

```
crates/validity-proto    the protocol: USB transport (nusb, `usb` feature, on by
                         default), TLS-like channel (RustCrypto: ECDH P-256,
                         AES-256-CBC, HMAC-SHA256), pairing, firmware upload,
                         calibration, flash, on-chip database, enrolment,
                         identification, session replay
crates/validity-vendor   validity-vendor: downloads Lenovo's package (curl),
                         checks it, extracts the two vendor files (the `inno`
                         crate), switches them into /var/lib/validity/vendor
crates/validity-daemon   validity-daemon: net.reactivated.Fprint (zbus), polkit,
                         logind suspend handling, recovery, an emulated sensor
crates/pam-validity      pam_validity.so, the module of the validity-fprint
                         pam-auth-update profile (shipped in the .deb)
packaging/               systemd unit, D-Bus files, udev rule, man page,
                         AppStream metadata, per-distribution recipes, APT files
ci/                      the CI (run.sh), end-to-end tests (e2e/), package
                         builds and install cycles (packages/)
fuzz/                    cargo-fuzz targets
tools/oracle/            python-validity scripts that generate the test vectors
docs/                    this guide, packaging, the phase 0 hardware report
```

In `validity-proto`:

- `tls.rs`: the channel's primitives, checked against python-validity via
  `tools/oracle/gen_tls_vectors.py` (vectors in `tests/vectors/`).
- `channel.rs`: the TLS flash (host key sealed with a key derived from the DMI
  product name and serial, certificate, sensor ECDH key signed by the firmware
  key), the handshake, and the application commands. Deliberate differences
  from the reference are documented where they are made.
- `transport.rs`: the `Transport` and `Entropy` traits, so sessions replay
  without hardware; `tests/handshake.rs` runs the handshake against an
  independent fake sensor.
- `usb.rs`, `cmd.rs`, `vendor.rs`: USB endpoints, status words, init, flash
  reads, the command blobs extracted from the vendor DLL by offset and hash.
- `init.rs`, `pairing.rs`, `fwext.rs`, `scanner.rs`, `db.rs`: opening a
  sensor, pairing, firmware upload, scanning, the on-chip database.

The module names follow python-validity's `validitysensor/`: read both side
by side to study the protocol.

In `validity-daemon`, `service` holds the D-Bus objects, `machine` the claim
and action rules (pure, unit-tested), `worker` the thread that owns the
sensor, `sensor` the non-destructive open sequence and result decisions, and
`fake` the emulated sensor used by the tests and the package cycles (hidden
option `--fake-sensor`).

## Build and test

Requirements: Rust 1.99 or later (edition 2024). No C library is needed to
build the daemon (the USB transport is pure Rust); `pam-validity` links
`libpam.so.0` (Debian: `libpam0g`). The daemon's integration tests need
`dbus-daemon`, validity-vendor's need `curl`.

```bash
cargo build
cargo test                                   # all tests
cargo test -p validity-proto <name>          # one test
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --check
VALIDITY_DLL=<synaWudfBioUsb.dll> cargo test # also checks blob extraction on the real DLL
VALIDITY_VENDOR_ARCHIVE=<nz3gf07w.exe> cargo test -p validity-vendor --test real
```

Warnings are denied in `Cargo.toml` itself, so a plain `cargo build` fails on
any. `unsafe` is forbidden, except in `pam-validity`, where it is denied and
allowed only in `src/ffi.rs` (the C side of the module, a `SAFETY` comment on
each block) and in the tests that load the module.

What the tests cover:

- test vectors from the Python reference;
- a full handshake against an independent fake sensor;
- exact-boundary tests derived from mutation testing;
- the replay machinery (log parser, `ReplaySensor`, masks, handshake checks)
  on synthetic logs in python-validity's debug-log format; real recordings
  replay only when `VALIDITY_TRACES` points to them
  (`VALIDITY_TRACES=<dir> VALIDITY_DLL=<dll> cargo test --test replay`), and
  never leave the machine;
- the daemon's D-Bus side on a private bus, and its binary;
- `pam_validity.so` through libpam itself (`crates/pam-validity/tests/pam.rs`),
  against a scripted fprintd on a private bus;
- validity-vendor against a synthetic Inno Setup installer written by the test
  suite.

## CI

`ci/run.sh` is the CI. GitHub Actions (`.github/workflows/ci.yml`) calls the
same jobs, in pinned Debian 13 containers, so a green local run means a green
CI run.

```bash
ci/run.sh                    # quick set: noai zizmor gitleaks fmt clippy test doc nousb
ci/run.sh all                # quick + msrv deny distro e2e fuzz mutants-diff (needs docker)
ci/run.sh clippy test        # selected jobs
ci/run.sh distro:fedora      # one distribution
```

| Job | What |
|---|---|
| `noai` | no AI tooling attribution in commits or files |
| `zizmor` | audits the workflows themselves |
| `gitleaks` | secrets, over the whole history |
| `fmt`, `clippy`, `doc` | rustfmt, clippy and rustdoc, warnings denied |
| `test` | `cargo test --workspace` |
| `nousb` | the protocol crate builds without its USB transport (what fuzzing uses) |
| `msrv` | `cargo check` with Rust 1.99.0 |
| `deny` | cargo-deny: licences, advisories, duplicates, sources |
| `audit` | cargo-audit (RustSec), daily in `audit.yml` |
| `distro[:<d>]` | the tests on Debian, Fedora, Arch Linux and Alpine |
| `e2e` | end to end, see below |
| `fuzz` | every fuzz target, `FUZZ_SECONDS` each |
| `mutants`, `mutants-diff` | mutation testing, see below |

Package builds and install cycles (Debian, Ubuntu 24.04 and 26.04, Fedora,
Arch Linux, Alpine, reproducibility, the APT repository) are a separate
script, `ci/packages/run.sh`, and workflow, `packages.yml`; see
[packaging.md](packaging.md). Every action and image is pinned by hash, and
every downloaded tool by version and SHA-256.

The pre-push hook runs the quick set on a clean worktree of each pushed
commit, with the host toolchain. Enable it once per clone:

```bash
git config core.hooksPath .githooks
```

### End-to-end test

`ci/run.sh e2e` (`ci/e2e/run.sh`, in `docker/Dockerfile.e2e`): a system bus with
polkit, the daemon on the emulated sensor, and the stock clients in front of
it: `fprintd-enroll`, `-verify`, `-list`, `-delete`, and `pam_fprintd` through
`pamtester`. The `validity-fprint` profile is then enabled with
`pam-auth-update` over fprintd's and checked line by line: on LightDM the
password first and the finger after an empty one, elsewhere the finger then
the password, nothing printed but `Access granted`, passwords working with no
daemon or no `pam_validity.so`, and `common-*` restored byte for byte when it
is disabled.

### Fuzzing

Four cargo-fuzz targets in `fuzz/fuzz_targets/`: `parsers`, `records`,
`tls_flash` and `handshake`. CI runs each for 30 s on every push and 10
minutes in the weekly run. Locally (nightly toolchain and cargo-fuzz, or the
fuzz image):

```bash
ci/run.sh fuzz
FUZZ_SECONDS=600 ci/run.sh fuzz
```

### Mutation testing

cargo-mutants runs over `validity-proto`, `validity-daemon` and
`pam-validity`: every mutant must make a test fail. `ci/run.sh mutants-diff`
checks the Rust code a push changes (CI: on every push and pull request);
`ci/run.sh mutants` checks all of it (CI: weekly, in 8 shards,
`MUTANTS_SHARD=k/8`). The few exclusions (equivalent mutants, code that only
runs against a real USB device) are each argued in `.cargo/mutants.toml`.
Results go to `mutants.out/`.

## Hardware

These need the sensor and root. Stop the daemon first (`sudo systemctl stop
validity-daemon`): only one process can hold the sensor.

```bash
cargo build --release --example probe --example session
sudo target/release/examples/probe <synaWudfBioUsb.dll>
sudo target/release/examples/session <dll> <calibration-file> list
sudo target/release/examples/session <dll> <calibration-file> identify 5
sudo target/release/examples/session <dll> <calibration-file> enroll <uid> <finger>
sudo target/release/examples/session <dll> <calibration-file> reset   # erases the sensor
sudo VALIDITY_FWEXT=<file.xpfwext> target/release/examples/session <dll> <cal> list   # pairs a blank sensor
```

`session` opens the sensor as `validity_proto::init::open` does: it pairs a
blank sensor, uploads the firmware extension when `VALIDITY_FWEXT` names it,
and calibrates when the calibration file is missing (then saves it).

### Traces

`VALIDITY_LOG=info|debug|trace` logs to stderr, each line prefixed with the
seconds since the start; the daemon logs the same lines with
`--trace-sensor-traffic`. Write the trace straight to a file:

```bash
sudo VALIDITY_LOG=trace target/release/examples/session <dll> <cal> enroll <uid> <finger> 2> session.log
```

A trace never contains command or reply contents (keys, templates, flash
data), so it can be shared. Check it for host names before posting it.

| Line | Meaning |
|---|---|
| `>plain> 3e (1 bytes)` | a command in the clear: opcode, length |
| `<plain< 3e (64 bytes, status 0000)` | its reply: opcode, length, status word |
| `>app> 5e (13 bytes)`, `<app< 5e (2 bytes, status 0000)` | the same over the encrypted channel |
| `>usb> 69 bytes`, `<usb< 85 bytes` | the USB transfers that carry them |
| `channel: handshake`, `channel: open` | the encrypted channel being opened |
| `wait: a finger (deadline 30s)` | a wait starts, with its deadline |
| `<int< 0300060000` | an interrupt; its first byte is the type (0 scan armed, 2 finger detected, 3 capture progress) |
| `<82< N bytes` | image data (calibration) |
| `WARN timed out after 2s waiting for the capture to start (last command 02, last interrupt none)` | a wait passed its deadline |

### Waits and timeouts

No wait on the sensor is unbounded. Each one has a deadline
(`validity_proto::session::Deadlines`); when it passes, the operation fails
with `Error::Timeout` and a warning names the last command and interrupt.

| Wait | Deadline | Longest seen in phase 0 |
|---|---|---|
| the finger, once the scan is armed (LED on) | 30 s, configurable | user dependent |
| scan armed after the capture command | 2 s | 6 ms |
| capture complete after the finger is down | 5 s | 856 ms |
| match result | 10 s | 829 ms (2 fingers enrolled) |
| each enrolment step | 5 s | 431 ms |
| image data (calibration) | 5 s | 103 ms |
| any other interrupt | 5 s | 6 ms |

The finger wait matches pam_fprintd's default timeout. In the daemon it is
`finger_timeout_ms` in `/etc/validity/validity.toml`. When it passes, a
verification ends with `verify-no-match`, and an enrolment reports
`enroll-retry-scan` and arms the scan again (fprintd keeps an enrolment
running until the client stops it). Any other deadline means the sensor
stopped answering: the run ends with `verify-disconnected` or
`enroll-disconnected` (pam_fprintd falls back to the password), the daemon
reboots the sensor and reopens it, and resets its USB port if even the
reboot command fails.

## Privacy

Captured USB sessions and flash dumps contain the sensor's serial number,
pairing keys and TLS session keys. Never commit them. Tests use synthetic
data; replays of real recordings read them from outside the repository
(`VALIDITY_TRACES`). gitleaks scans the whole history in CI.

## Releases

A tag `v<version>` (the version in `Cargo.toml`) runs
`.github/workflows/release.yml`:

1. a gate: the tag names the version, and CI and Packages are green on the
   tagged commit;
2. one vendored source tarball, every package built from it in its pinned
   image and run through its install cycle, each .deb rebuilt and compared;
3. `SHA256SUMS`, signed with the APT repository's signing subkey;
4. a build provenance attestation for every file, verified at once;
5. a draft GitHub release, which a maintainer reviews and publishes;
6. publication jobs, each enabled by a repository variable: the APT
   repository (enabled); crates.io, COPR and the AUR are off. Crates are
   published by hand with `cargo publish` (0.1.1 is on crates.io); Fedora,
   Arch and Alpine users download the packages from the GitHub release.

`workflow_dispatch` is a dry run. Details, the key and the one-time setup:
[packaging.md, Releases](packaging.md#releases).

## Contributing

Issues and pull requests are welcome.

- Bug reports: the USB ID (`lsusb`), the laptop model, the distribution and
  kernel versions, and a trace (see [Traces](#traces)).
- Code must pass `ci/run.sh` (enable the pre-push hook). Behaviour changes
  come with tests, and mutation testing must stay at zero survivors.
- Every change that alters behaviour, commands, layout or CI updates the
  documentation in the same commit.
- Code ported from python-validity keeps its attribution in `NOTICE`. Code
  from GPL projects (open-fprintd, fprintd) is not accepted.
- Contributions are under the MIT license.
